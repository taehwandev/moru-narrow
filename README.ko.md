# moru-narrow

[English](README.md) | **한국어**

> 영문 `README.md`가 기준 문서이고, 이 문서는 한국어 번역입니다. 내용이 다르면 영문을 따릅니다.

> **rg는 이름이 나온 모든 줄을 알려 준다. moru-narrow는 그중 고쳐야 할 줄을 알려 준다.** 히트를 하나도 버리지 않고, 순서와 먼저 보여 줄 것만 바꾼다.

`moru-narrow`는 코딩 에이전트와 사람을 위해 `rg -w <이름>` 결과를 후처리한다. 모든 히트를 유지하면서 순위를 매기고,
먼저 확인할 파일과 **줄 범위**를 출력한다. 인덱스도, 데이터베이스도, 모델 호출도, 상주 프로세스도 없다. Python 표준 라이브러리와
[ripgrep](https://github.com/BurntSushi/ripgrep)만 쓴다.

> 범위: **시그니처 변경**(매개변수를 추가하거나 바꾼 뒤 무엇이 깨지는지 찾기). 일반 `rg`를 대체하지 않는다. 변수 이름 변경, 로직 버그 추적, 설정 문자열 검색에는 `rg`를 그대로 쓴다.
>
> 상태: 알파 / 실험적. MIT 라이선스. 예시는 `moru-narrow` 명령(별칭 `mnarrow`)을 쓴다. 저장소를 내려받아 쓸 때는 `python3 -m moru_narrow`로 실행한다.

## 한눈에 보기

- **무엇을 하나:** `rg -w 이름` 뒤에, 고쳐야 할 소수의 파일과 줄 범위를 순위를 매겨 보여 주고 나머지는 `--all` 뒤로 숨긴다. 버리는 것은 없다.
- **놓치는 파일이 있나:** 컴파일러를 정답으로 확인했다. Kotlin 과제 217개 모두에서 정답 파일이 전부 목록에 있었고(규칙 일부는 그 과제들을 보고 고쳤다), 새로 뽑은 TypeScript 세트에서는 194개 중 191개 과제(파일 기준 99.3%)였다. 드물게 놓치는 것은 이름이 아예 나오지 않는 파일이다.
- **코딩 에이전트에게 도움이 되나:** 6개 시험 설정 어디에서도 컴파일 성공률이 기준보다 떨어지지 않았다. 컨텍스트 토큰은 다섯 설정에서 9.8~34.5% 줄었고, 여섯째(TypeScript의 Codex)는 오차와 구분되지 않는다.
- **조건:** 에이전트에게 `rg`를 다시 돌리지 말라고 함께 알려 줄 때만 절감이 나왔다. 그 문장이 없으면 한 시험(Kotlin, Haiku, 과제 57개)에서 비용이 10.3% [과제당 +0.0003, +0.0009 달러] 늘었다.

## 빠른 시작

Python 3.9 이상과 [ripgrep](https://github.com/BurntSushi/ripgrep)(`rg`)이 `PATH`에 있어야 한다. 다른 의존성은 없다. 모루 Core나 다른 도구는 필요 없다.

```bash
pipx install moru-narrow     # 또는: uv tool install moru-narrow / pip install moru-narrow
moru-narrow <이름> --repo /path/to/your/project                # Kotlin+Gradle 또는 TypeScript, 자동 감지
```

설치하지 않고 쓰려면 저장소를 내려받아 `git clone https://github.com/taehwandev/moru-narrow && cd moru-narrow && python3 -m moru_narrow <이름> --repo ...`로 실행한다.

[PyPI](https://pypi.org/project/moru-narrow/)에 올라가 있고 npm에는 없다. `pip install moru-narrow`는 macOS의 깨끗한 가상환경에서 시험했다(버전 26.45.0, Python 3.9.6과 3.13 빌드). 다른 플랫폼은 시험하지 않았다. 최신 커밋을 따라가려면 Git에서 설치한다: `pipx install git+https://github.com/taehwandev/moru-narrow`.

## 코딩 에이전트에 적용하기

에이전트가 사용법을 알아야 도구가 도움이 된다(절감 효과 항목 참고: "`rg`를 다시 돌리지 마라"는 문장이 없으면 비용이 늘었다). 명령 하나로 그 지시를 등록한다.

```bash
moru-narrow --install                # 에이전트 스킬을 ~/.claude/skills/(Claude Code)와 ~/.agents/skills/(Codex 등 agent-skills 도구)에 설치
moru-narrow --install --project      # 같은 내용을 ./.claude, ./.agents에 설치해서 git으로 팀과 공유
moru-narrow --install --agents-md    # 스킬을 지원하지 않는 도구(예: Cursor)는 ./AGENTS.md에 표시 구간을 추가
```

다시 실행해도 안전하다. 이미 있는 `SKILL.md`는 그대로 두고(`--force`로 덮어쓴다), `AGENTS.md`의 표시 구간만 제자리에서 바꾸며 다른 내용은 건드리지 않는다. `--target claude|agents`로 스킬 설치 위치를 하나로 줄일 수 있다. 설치되는 문장은 영문 README의 인용문과 같고, 에이전트 시험에 쓴 지시를 바탕으로 했다(표현은 다르다).

측정한 문장과 표현이 같지 않고, 마지막 문장(다른 작업이나 지원하지 않는 언어에서는 평범한 `rg`를 쓴다)은 새로 넣은 것이다. 시험 과제는 시그니처 변경뿐이었고 그에 맞춘 프롬프트만 썼다. 셸 명령을 실행할 수 있는 에이전트라면 `moru-narrow`를 직접 호출해도 된다.

## 왜 만들었나

함수 시그니처를 바꾸면 깨지는 곳을 전부 찾아야 한다. `rg -w 이름`은 그 곳을 모두 찾아 주지만, 주석, 문자열, 다른 모듈의
같은 이름 함수, 관련 없는 파일도 함께 준다. Kotlin 모노레포에서는 **3~4개 파일이 깨지는 변경에 60개 파일**을 돌려주었다.
에이전트는 그것을 전부 읽는다.

코드 그래프 인덱스가 당연한 해법으로 보였다. 같은 Kotlin 저장소에서 문법 수준의 코드 그래프 인덱스를 측정했는데 에이전트 단계에서는
효과가 없었다. 위치만 돌려줄 때는 측정 가능한 비용 차이가 없었고, 소스 코드를 돌려주면 비용이 약 +45.5% 늘었다(그 실행에는 MCP 연결 부담도 섞여 있어서 증가분 일부는 그래프 자체 때문이 아니다).
인덱스를 만들어야 하고, 편집할 때마다 동기화해야 하며(동기화 전에는 오래된 결과가 나온다), `moru-narrow`는 `rg`를 그때그때 실행하므로
구축 단계도 오래된 결과도 없다.

## 동작 방식

1. `rg -nw <이름>`으로 히트를 모은다(테스트 파일 제외).
2. 줄마다 역할을 붙인다: `use`, `import`, `override`, `declaration`, `comment`, `string`, `named-arg` 등.
3. 강한 역할(`use`/`import`/`override`)이 있고 **선언을 볼 수 있는** 파일을 **1순위**로 올린다.
   - Kotlin: Gradle `project()` 의존으로 모듈에 도달할 수 있고, 같은 패키지이거나 해당 패키지를 import한다.
   - TypeScript: 선언 파일을 import하거나(상대 경로와 `tsconfig` 별칭, 재수출 barrel 파일 포함), 그 파일을 import하는 래퍼를 import해서
     `X.이름`으로 부르거나, 선언 파일 자체다.
4. 나머지는 2/3순위로 **내릴 뿐**이다. **필터는 순위만 낮추고 `--all`은 `rg`가 찾은 모든 것을 보여 준다.**
5. 여러 줄에 걸친 호출은 범위(`19-22`)로 돌려준다. 컴파일러가 인자가 있는 줄에서 오류를 내기 때문이다.

```text
moru-narrow <이름> [--repo DIR] [--decl FILE] [--all] [--json] [--lang kotlin|ts]
```

언어는 자동으로 감지한다(`tsconfig.json` 또는 Gradle 빌드).

## 숫자 읽는 법

| 용어 | 여기서의 뜻 |
| --- | --- |
| **정답 파일** | 함수에 필수 첫 매개변수(`traceId`)를 추가한 뒤 컴파일이 깨지는 프로덕션 파일. 판정은 우리가 아니라 컴파일러가 한다. |
| **재현율** | 정답 파일이 1순위에 들어 있는지. 표는 정답 파일이 전부 들어 있던 과제 수를 센다(`23/23`). TypeScript 행은 파일 수도 함께 적었다(`428/431` = 정답 파일 3개가 목록에 없었다). |
| **1순위** | moru-narrow가 먼저 읽으라고 알려 주는 파일. |
| **`rg -w` 파일 / 줄** | 같은 이름으로 일반 ripgrep을 돌렸을 때 나오는 양. 이겨야 할 기준선이다. |
| **새 세트** | 규칙을 동결한 뒤에 뽑은 후보. 어떤 조정에도 쓰지 않았으므로 공정한 시험이다. |
| **기준 / moru-narrow 사용** (에이전트 시험) | 같은 코딩 에이전트, 같은 과제, 같은 프롬프트. 기준 조건은 `rg`, `ls`, 파일 읽기를 쓸 수 있다. 다른 조건은 여기에 도구와 "이 목록에서 고치고, 같은 이름으로 rg를 다시 돌리지 마라"는 문장을 더 받는다. |
| **컴파일 통과** | 에이전트의 수정 뒤 프로젝트가 컴파일된다(Kotlin: Gradle, TypeScript: `tsc --noEmit`). TypeScript 실행은 선언에 매개변수가 실제로 추가됐는지도 함께 본다. 아무것도 안 고친 에이전트가 통과로 잡히는 일을 막기 위해서다. |
| **컨텍스트 토큰** | 실행 전체에서 모델이 처리한 입력 토큰(캐시된 것 포함). 얼마나 많이 읽었는지에 대한 대용품이다. |
| **비용** | Claude CLI가 보고하는 API 환산 추정 가격이며 실제 청구액이 아니다. Codex는 보고하지 않아 해당 없음으로 적었다. |
| **`[a, b]` 구간** | 과제 단위 짝 부트스트랩(10,000회 재표집)의 95% 범위. 과제를 다시 뽑고 같은 과제에서 두 조건을 비교한다. 범위가 0을 포함하면 차이를 오차로 본다. |
| **과제 x 반복** | 과제 수 곱하기 과제당 반복 횟수. 같은 과제의 반복은 평균을 낸 뒤 비교한다. |

## 놓치는 파일은 없나

정답은 **컴파일러**다. 함수(또는 Kotlin 생성자)에 필수 첫 매개변수 `traceId: String` / `traceId: string`을 추가하고
컴파일해서 실패하는 프로덕션 파일을 정답으로 삼았다.

| 세트 | 과제 수 | `rg -w` 파일 / 줄 | moru-narrow 1순위 파일 / 줄 | 정답 파일이 모두 1순위에 있던 과제 |
| --- | ---: | --- | --- | ---: |
| Kotlin, 이름이 겹치는 함수 23개를 골라서 | 23 | 60.4 / 139 | 8.8 / 18 | 23/23 |
| Kotlin, 따로 둔 검증 함수 | 120 | 68.3 / 281 | 3.3 / 5 | 120/120 |
| Kotlin, 검증용 중 노이즈 큰 부분집합(`rg` 20개 이상, 정답의 2배 이상) | 57 | 132.9 / 571 | 3.8 / 7 | 57/57 |
| Kotlin, 생성자 변경 | 74 | 14.9 / 36 | 8.8 / 17 | 74/74 |
| TypeScript, **새** 함수(v3 규칙을 먼저 동결) | 194 | 3.5 / 7 | 2.5 / 6 | 191/194 (파일: 428/431, 99.3%) |
| TypeScript, 새 함수 중 노이즈 큰 것(`rg` 5개 이상) | 28 | 9.5 / 20 | 8.2 / 18 | 28/28 (파일: 193/193) |

읽을 때 주의할 점:

- Kotlin 규칙은 처음 검증 세트에서 놓친 것을 본 뒤 고쳤다(정규식 버그 두 개). 그래서 Kotlin 세트는 **완전히 독립적이지 않다**.
  TypeScript 새 세트는 규칙을 동결(sha256 기록)한 뒤에 채점했다.
- TypeScript에서 남은 미스는 실패한 파일에 **이름이 아예 나오지 않는** 경우다(타입이 다른 함수를 거쳐 전파됨).
  `rg` 기반 도구는 어떤 것도 이것을 찾을 수 없다.
- 줄 단위: 오류 줄이 추천 범위 안에 들어간 비율은 Kotlin 함수 90%, Kotlin 생성자 ±8줄 이내 96%, TypeScript 함수 90%다.
  범위는 힌트로, 파일은 보장으로 쓴다.
- TypeScript 정답은 TypeScript API로 메모리에서 만들었고 비공개 Next.js 저장소 하나에서, Kotlin은 비공개 Compose Multiplatform
  저장소 하나에서 측정했다. 두 저장소는 이곳에 공개하지 않았다.

## 에이전트의 비용이 줄어드나

같은 과제, 같은 프롬프트 템플릿, 두 조건, 과제 단위 짝 부트스트랩(10,000회 재표집, 95% 구간). 로컬 로그인만 썼다.
비용은 CLI가 보고하는 API 환산 추정값이다.

| 설정 | 컴파일 통과 (기준 -> moru-narrow 사용) | 컨텍스트 토큰 | 비용 |
| --- | --- | --- | --- |
| Kotlin, Haiku, 23개 x 2회 | 46/46 -> 46/46 | **-34.5%** [-107k, -37k] | **-24.2%** |
| Kotlin, Haiku, 57개 x 2회 | 112/114 -> 114/114 | **-19.2%** [-36k, -18k] | **-16.4%** |
| Kotlin, Codex terra, 23 x 2 | 44/46 -> 45/46 | **-14.2%** [-22.8%, -6.2%] | 해당 없음 |
| Kotlin, Codex terra, 57 x 2 | 112/114 -> 114/114 | **-9.8%** [-14.6%, -5.3%] | 해당 없음 |
| TypeScript, Haiku, 28 x 2 | 56/56 -> 56/56 | **-22.2%** [-29.4%, -15.3%] | **-11.1%** [-17.3%, -4.3%] |
| TypeScript, Codex terra, 28 x 2 | 56/56 -> 56/56 | -6.5% [-13.5%, 0.0%] (0에 닿음) | 해당 없음 |

**도구만큼 에이전트에게 주는 지시가 중요하다.** 첫 Kotlin 실험에서는 에이전트가 같은 목록을 받고도 그 뒤에 `rg`를 계속
다시 돌렸고, 더 큰 Haiku 세트에서 비용이 오히려 10.3% **늘었다**(컨텍스트 +12.8%). "이 목록에서 호출 지점을 바로 고치고, 같은 이름으로
`rg`를 다시 돌리지 마라. 목록이 불완전해 보일 때만 --all을 써라"라는 한 문장을 더하자 실행당 `rg` 호출이 2.4번에서 0.02번으로
(Kotlin, Codex, 과제 23개), 2.8번에서 0.5번으로(TypeScript, Haiku) 줄었고 위 표가 나왔다.
이 수정한 프롬프트는 첫 결과를 본 뒤에 썼으므로 절감 효과는 탐색적인 결과로 읽어야 하고, 도구와 지시문을 함께 배포해야 한다.

**어렵게 배운 것.** 첫 TypeScript 에이전트 실행은 기준보다 10개 과제를 더 실패했다(33/44 대 43/44). 컴파일러가 지목한 파일은
모두 목록에 있었다. 놓친 것은 *선언 파일 안*의 호출이었고, 첫 버전은 파일이 자기 자신을 import하지 않는다는 이유로 이를 숨겼다.
오프라인 정답도 선언 파일을 빼고 만들어서 오프라인 검사로는 이것이 보이지 않았다. 수정(v3): 그 줄들을 1순위에 둔다.
교훈: 오프라인 검증만 하지 말고 실제 에이전트 루프로 검증하라.

## 한계

- 언어: Kotlin + Gradle, TypeScript. 언어마다 작은 프로필(역할 패턴, 선언을 보는 방법)이 필요하다. 동적 언어는 정답 만드는 방식부터 다르다.
- **변경 모양 하나**(필수 첫 매개변수 추가)와 **언어당 저장소 하나**에서 검증했다.
- React 컴포넌트는 범위 밖이다(JSX에는 위치 기반 첫 매개변수가 없다).
- 절감은 모델에 따라 다르다. TypeScript 저장소의 Codex에서는 뚜렷한 감소가 없었다(-6.5%, 구간이 0에 닿음). 그곳에서는 `rg`가 이미 정확했고
  (함수 기준 평균 3.5개 파일) 에이전트가 과제당 명령을 3번 정도만 실행했다. 이유는 따로 검증하지 않았다.
- 표본이 작다(과제 28~57개, 과제당 2회). TypeScript는 기준 조건에서도 모든 실행이 통과해서 통과율로는 개선을 보일 수 없고, 깨지지 않았다는 것만 확인된다.
- 에이전트 시험은 저자의 로컬 CLI 로그인으로 비공개 소스를 모델 제공자(Anthropic, OpenAI)에 보냈다.

## 재현

평가 도구(에이전트 실행기, 컴파일러 정답 생성기, 채점기)는 아직 이 저장소에 없다. 로컬 경로와 비공개 저장소 정보가 들어 있어서
정리가 필요하다. `results/`에 집계 표가 있다. 방법은 위에 적었다. 필수 첫 매개변수를 추가한 뒤 생기는 컴파일러 오류를 정답으로
삼았고, TypeScript 새 세트는 규칙을 동결(해시 기록)한 뒤에 채점했다.

## 버전 규칙

주간 CalVer `YY.WW.N`(체계 이름 `calver-weekly`)을 쓴다. 예: `26.45.0`. 두 자리 연도, 주차, 그리고 주마다 `0`에서 시작해 배포한 패키지마다 하나씩 늘어나는 릴리즈 횟수다. 주차는 한국 달력(Asia/Seoul, 월요일 시작)을 따른다. git 태그에는 `v` 접두사를 붙이고(`v26.45.0`), 패키지 메타데이터에는 붙이지 않는다. Python은 앞에 0이 붙은 주차를 정규화하므로 5주차는 PyPI에서 `26.5.0`으로 보인다. 날짜 기반 버전이어서 호환성을 알려 주지 않는다. 알파인 동안에는 업그레이드 전에 커밋 기록을 확인한다.

## 상태

알파. PyPI에는 있고 npm에는 없다. 단위 테스트는 아직 없다. 순위 매기기는 위에 적은 컴파일러 정답으로 검증했고, `--install`은 임시 홈 디렉터리에서 손으로만 확인했다(새 설치, 재실행, `--project`, `--agents-md` 반복 실행). 이슈와 다른 저장소에서의 결과를 환영한다.
